## 1. Locked decisions (do not change)

| # | Decision |
|---|----------|
| 1 | Parent–student linking is **code-first**: student generates a printable code; parent registers independently and enters (index number + code) to link. **Code lives on the student** (see §3 resolved amendments). |
| 2 | Academic structure is **configurable** via `school_config.academic_structure`: `'semester'` (2 periods, tertiary) or `'term'` (3 periods, JHS/SHS). Period labels come from `school_config.period_labels`. **Exactly one** period is active at any time. |

## 1a. Resolved amendments (already decided — do not re-open)

These supersede any earlier draft of the schema. Apply them exactly.

### A. Access-code home (`linkCode` on `User`)

The original draft put `accessCode` on `ParentStudentLink`, which cannot work: the code is generated by the student **before** any parent is known, but `ParentStudentLink.parentId` is required. The code must live on the student.

- `User` gains `linkCode: String? @unique` (12-char Crockford base32 uppercase) and `linkCodeUpdatedAt: DateTime?`.
- `ParentStudentLink` **drops** `accessCode` entirely (column, unique index, and CHECK constraint).
- The `access_code_format` CHECK moves from `ParentStudentLink."accessCode"` to `"User"."linkCode"`.
- Behaviour (unchanged in spirit from §7 rule 2):
  - Every unarchived student has exactly one valid `linkCode` at any time; generated on account creation, or via `POST /parent/regenerate-code`.
  - `POST /parent/link {indexNumber, accessCode}` runs in a single transaction: look up the student by `indexNumber`, match `accessCode` against their current `linkCode`, insert `ParentStudentLink`, then regenerate the student's `linkCode` and touch `linkCodeUpdatedAt`. A reused code fails because the student's code has already rotated.
  - `POST /parent/regenerate-code` (student auth) replaces `linkCode`, touches `linkCodeUpdatedAt`, returns the new value, and writes `ActivityLog` action `LINK_CODE_REGENERATED`.
  - `GET /parent/wards` unchanged — reads `ParentStudentLink WHERE parentId = caller.id`.

### B. FK index split (non-negotiable)

Prisma and Postgres do not auto-index FK columns. Indexes must be added explicitly, in **two** migrations, not deferred wholesale:

**Sprint 2 migration (`20250101000002_fk_indexes`):**

```sql
CREATE INDEX IF NOT EXISTS idx_notification_user_created
  ON "Notification" ("userId", "createdAt" DESC);
CREATE INDEX IF NOT EXISTS idx_performance_student_period
  ON "Performance" ("studentId", "periodId");
CREATE INDEX IF NOT EXISTS idx_fee_student_status
  ON "Fee" ("studentId", "status");
CREATE INDEX IF NOT EXISTS idx_parentlink_parent
  ON "ParentStudentLink" ("parentId");
CREATE INDEX IF NOT EXISTS idx_parentlink_student
  ON "ParentStudentLink" ("studentId");
-- Not strictly an FK, but role-scoped lookups in later sprints need it.
CREATE INDEX IF NOT EXISTS idx_userrole_role
  ON "UserRole" ("roleId");
```

The composite `Notification ("userId", "createdAt" DESC)` and composite
`Performance ("studentId", "periodId")` are **required** — a single-column index on
`userId` or `studentId` will not satisfy `WHERE userId = ? ORDER BY createdAt DESC LIMIT 20`
or `WHERE studentId = ? AND periodId = ?` efficiently; Postgres would index-scan then sort.

**Deferred to sprint 12 (with `EXPLAIN ANALYZE` on a 2,000-row fixture, not blind):**
`CourseRegistration ("courseId", "periodId")`, `Performance ("courseId", "periodId")`,
`ActivityLog ("userId")`, `ActivityLog ("action")`, `Fee ("academicYearId")`.

## 6. API contract

All routes under `/api`. JSON in / JSON out. Auth via httpOnly JWT cookie. Every mutating request writes an `ActivityLog` row (middleware). All list endpoints paginate (`?page=&pageSize=`, default 20, max 100). All request bodies validated with Zod.

### Auth

```
POST /auth/register          body: {username, email, password, fullName, roleCode, parentEmail?}
POST /auth/login             body: {identifier, password}   // identifier = username OR indexNumber
POST /auth/totp/setup        auth                         // returns {secret, qrDataUrl}
POST /auth/totp/verify       auth  body: {code}           // enables TOTP
POST /auth/totp/check        body: {tempToken, code}      // 2FA completion → real JWT
POST /auth/refresh           // rotates JWT
POST /auth/logout
POST /auth/password/forgot   body: {email}
POST /auth/password/reset    body: {token, newPassword}
POST /auth/switch-role       auth  body: {roleCode}       // multi-role picker
```

2FA flow: if `user.totpEnabled`, `POST /auth/login` returns `{ requiresTotp: true, tempToken }` (5-min TTL, no permissions). `POST /auth/totp/check` exchanges `tempToken + code` for the real JWT. Failed TOTP counts toward lockout.

Lockout: 5 failed password attempts → 15-min cooldown on that `(identifier, IP)` pair, logged to `ActivityLog`. When the identifier resolves to a known user, set `ActivityLog.userId`; always log both `identifier` and `ip` in `details`.

## 7. Business rules (non-negotiable)

1. **Exactly one active period.** Any write that references `periodId` must verify the period is active OR the writer has `performance.override`. Students can only register courses for the active period.

2. **Parent access code is 12-char Crockford base32, stored on `User.linkCode`.** Generated server-side with `crypto.randomBytes(8)`, mapped through the Crockford alphabet, uppercased. Regenerable by the student; the old code becomes invalid immediately (because `linkCode` is replaced, and the field is `@unique`).

3. **Parent verify endpoint is rate-limited** to 5 attempts per IP per hour and 5 attempts per parent per hour. Every failed attempt logged to `ActivityLog` with `action='PARENT_LINK_FAILED'`.

4. **Ownership rule for `/performance/student/:id`:** caller is (a) that student, (b) a linked parent, (c) a teacher of a course the student is registered in for the active period, (d) admin. Otherwise 403.

5. **Essays:** on assessment submit, `performance.essayPending = true` and `score` records only the auto-graded portions. `POST /assessments/:id/grade-essay` updates `score`, `maxScore`, and clears `essayPending`. AI can suggest a score against the marking guide — the teacher confirms; the confirmed value is what's stored.

6. **Short course progress never touches `performance`.** Enforce by having no code path; add a unit test asserting the tables are disconnected.

7. **Archive** sets `archived_at`, `archive_reason`, `retention_until = now + school_config.retention_years`. Archived users cannot log in. **Purge** requires `retention_until < now` AND `permission:user.purge` AND a reason string; the purge is written to `ActivityLog` before deletion.

8. **Fee batch fanout** creates one `Notification` row per (linked parent, channel) per student in the batch. Email send via BullMQ queue (`email`). A batch with 500 students must return `{batchId, queued: 500}` in under 1s.

9. **Admin 2FA is mandatory.** All three admin roles must have `totp_enabled = true` before any admin route will respond. On first login for an admin without TOTP, the JWT is scoped to `/auth/totp/setup` only.

10. **Email fanout and the retention purge are queued jobs.** AI question generation is synchronous with a 30-second timeout — the teacher is waiting for the output. Rate-limit AI generation to 10 requests per teacher per hour (Redis). If OpenAI times out, return 504 with a retry hint.

11. **Every mutating request logs to `ActivityLog`** via middleware. Include `userId`, `action`, `details` (sanitised — never log passwords or tokens), `ipAddress`.

12. **Passwords bcrypt cost 12.** JWT httpOnly, Secure, SameSite=Lax, 8h TTL, rotation on refresh. TOTP secrets encrypted at rest with AES-256-GCM using `TOTP_ENCRYPTION_KEY` env.

13. **AI generation input validation:** `text.length` must be ≥ 200 and ≤ 30,000. Reject inputs where >40% of lines are under 30 chars and end without punctuation (looks like a table of contents) with a 400 asking for fuller content. When `text.length > 20,000`, include in the system prompt: "This is a long excerpt; distribute questions across its major sections, not just the opening."

## 8. Five critical tests (mandatory, CI-blocks merge)

**Test 1 — Parent authz.**
- Parent A linked to Student A, Parent B linked to Student B.
- Parent B `GET /parent/wards/{studentA}/performance` → 403.
- Parent A same call → 200 with correct data.
- Parent B `POST /parent/link` with Student A's index + Parent A's code → 403.
- 6 rapid wrong-code attempts from the same parent within an hour → 429 on the 6th.

**Test 2 — Archive + retention.**
- Registrar `POST /admin/users/:id/archive` → 403.
- Principal archives a user → user cannot log in → default `GET /admin/users` excludes them → `GET /admin/users?archived=true` shows them → their performance records remain queryable.
- Principal `POST /admin/users/:id/purge` with `retention_until` in the future → 400.
- Fast-forward `retention_until` to yesterday, retry → 200 and cascade-deletes.

**Test 3 — Essay submission + grading.**
- Student takes a mixed assessment (2 objective + 1 essay), submits.
- Response shows `score = objective correct`, `essayPending = true`.
- Student `POST /assessments/:id/grade-essay` → 403.
- Teacher grades essay → `performance.score` and `maxScore` update, `essayPending = false`.
- Student `GET /performance/mine` shows combined score.

**Test 4 — Admin 2FA flow.**
- Seed principal without TOTP → login returns `{requiresTotpSetup: true}` and JWT restricted to `/auth/totp/setup`.
- `POST /admin/users` with restricted JWT → 403.
- Complete `POST /auth/totp/setup` then `POST /auth/totp/verify` with code from the same secret → 200.
- Logout, login → `{requiresTotp: true, tempToken}`.
- `POST /auth/totp/check` wrong code → 401; 5 wrong codes → 429.
- Correct code → real JWT → `GET /admin/users` → 200.

**Test 5 — AI generation from text.**
- `POST /assessments/ai-generate` with `text: ""` → 400.
- text of 50 chars → 400 (below minimum).
- text of 31,000 chars → 400 (over max).
- text of 1,000 chars that is 80% short lines ending without punctuation → 400 (looks like TOC).
- Valid text with `objective:3, fill_blank:2, essay:1` → 200 with `{objective:[], fill_blank:[], essay:[]}` shape; each objective question has exactly 4 options and an answer in A–D.
- 11th request within an hour → 429.
- Student calling the endpoint → 403.
